# สเปกระบบประเมินพนักงานพร้อมพอร์ตผลงาน

Oct 14, 2026 · @fdev

## ภาพรวมและเป้าหมาย

ระบบนี้ทำให้การประเมินพนักงานอิงจากหลักฐานผลงานที่บันทึกไว้ตลอดปี ไม่ใช่ความจำของหัวหน้าหรือความสามารถในการนำเสนอของพนักงาน

**ปัญหาที่แก้:** ระบบประเมินทั่วไปให้เครดิตคนพูดเก่งและขายงานเก่ง ส่วนคนที่ทำงานเงียบๆ แต่ทำเยอะมักถูกมองข้าม

**แนวคิดหลัก:**

- **พอร์ตผลงานเป็นแกนกลาง** ทุกคนมีพอร์ตที่รวมโปรเจกต์ บทบาท หน้าที่ และผลงานพร้อมหลักฐาน
- **ประเมินจากหลักฐาน** ตอนให้คะแนน ระบบแสดงพอร์ตของคนนั้นข้างๆ ฟอร์ม
- **กรอกง่าย** คนที่ไม่ถนัดเขียนยาวต้องใช้ได้ ไม่งั้นระบบจะเอนเอียงเหมือนเดิม
- **ความเป็นธรรมต้องออกแบบตั้งแต่ต้น** ทั้งเรื่องสิทธิ์ การไม่ระบุตัวตน และการล็อกผลหลังปิดรอบ

## ผู้ใช้และสิทธิ์

มี 4 บทบาท แต่ละบทบาทเห็นและทำได้ไม่เท่ากัน เพราะข้อมูลประเมินเป็นข้อมูลอ่อนไหว จึงกำหนดสิทธิ์ตั้งแต่เวอร์ชันแรก

| บทบาท | เห็นอะไรได้ | ทำอะไรได้ |
|---|---|---|
| พนักงาน | พอร์ตตัวเอง, ผลประเมินตัวเองหลังปิดรอบ | บันทึกผลงาน, ยืนยันผลงานเพื่อนร่วมทีม, ประเมินตัวเอง |
| หัวหน้า | พอร์ตและผลของลูกทีมตัวเอง | ประเมินลูกทีม, เติมผลงานให้ลูกทีม (ลูกทีมต้องกดยืนยัน) |
| HR | ภาพรวมทั้งองค์กร, รายงาน | สร้างแบบประเมิน, เปิด/ปิดรอบ, ปรับเทียบคะแนน |
| แอดมิน | ข้อมูลระบบและ audit log | จัดการบัญชี โครงสร้างองค์กร และสิทธิ์ |

> **ข้อสังเกต:** คะแนน 360° ต้องไม่ระบุตัวตนผู้ประเมิน แม้แต่ HR ก็เห็นเฉพาะข้อมูลสรุปรวม

### การกำหนดบทบาท

บทบาทซ้อนกันได้ คนหนึ่งคนมีสิทธิ์รวมของทุกชั้นที่ตัวเองมี เช่น หัวหน้าฝ่าย HR เป็นทั้งพนักงาน หัวหน้า และ HR

| ชั้น | ใครได้ | กำหนดอย่างไร | เก็บในระบบไหม |
|---|---|---|---|
| พนักงาน | ทุกคนที่มีบัญชี | ได้โดยอัตโนมัติ | ไม่เก็บ |
| หัวหน้า | คนที่มีลูกทีมโดยตรง | คำนวณจาก `manager_id` ของลูกทีม | ไม่เก็บ คำนวณทุกครั้ง |
| HR | คนที่ได้รับสิทธิ์ | แอดมินเป็นคนกำหนด | เก็บ |
| แอดมิน | คนที่ได้รับสิทธิ์ | แอดมินเป็นคนกำหนด ส่วนแอดมินคนแรกตั้งตอนติดตั้งระบบ | เก็บ |

กติกา:

1. หัวหน้าเห็นเฉพาะลูกทีมโดยตรง สิทธิ์ข้ามระดับ (เช่น ผู้อำนวยการ) จะมาพร้อมขั้นตอนอนุมัติในเฟส 3
2. ห้ามใช้สิทธิ์ที่สูงกว่าพนักงานกับข้อมูลของตัวเอง เช่น HR ปรับเทียบคะแนนตัวเองไม่ได้ ข้อมูลของตัวเองได้รับสิทธิ์ระดับพนักงานเสมอ
3. แอดมินไม่ใช่ HR แอดมินจัดการบัญชี โครงสร้างองค์กร และสิทธิ์ และดู audit log ได้ แต่ไม่เห็นคะแนน คอมเมนต์ หรือพอร์ต เว้นแต่จะได้สิทธิ์ HR ด้วย
4. ความไม่ระบุตัวตนของ 360° อยู่เหนือทุกบทบาท แม้แต่แอดมินก็ดูตัวผู้ประเมินไม่ได้
5. เปลี่ยนสายบังคับบัญชาแล้ว สิทธิ์เปลี่ยนตามทันที แต่การประเมินที่ส่งไปแล้วยังบันทึกผู้ประเมินตามจริง ณ ตอนนั้น
6. การให้หรือถอนสิทธิ์ และการเปลี่ยน `manager_id` ต้องบันทึกใน AuditLog

## ฟังก์ชัน

แบ่งเป็น 3 เฟส เฟส 1 คือแกนที่ทำให้ระบบใช้งานได้และมีจุดเด่นเรื่องพอร์ต ส่วนเฟสถัดไปต่อยอดทีหลัง

| เฟส | ฟังก์ชัน | คำอธิบายสั้นๆ |
|---|---|---|
| 1 (MVP) | ล็อกอินและสิทธิ์ตามบทบาท | แต่ละบทบาทเห็นและทำได้ไม่เท่ากัน |
| 1 (MVP) | จัดการพนักงานและโครงสร้างองค์กร | แผนก ตำแหน่ง สายบังคับบัญชา ใช้กำหนดว่าใครประเมินใคร |
| 1 (MVP) | โปรเจกต์และทีม | สร้างโปรเจกต์ ระบุสมาชิก บทบาท และหน้าที่ของแต่ละคน |
| 1 (MVP) | บันทึกผลงาน (Contribution log) | เขียนสั้นๆ พร้อมลิงก์หลักฐาน (PR, เอกสาร, ตั๋วงาน, ภาพหน้าจอ) |
| 1 (MVP) | ผลกระทบ (Impact) และแท็กทักษะ | บอกว่างานช่วยอะไร และผูกกับทักษะ เช่น Python, การเป็นพี่เลี้ยง |
| 1 (MVP) | ให้เครดิตกันเอง (Endorse) | เพื่อนร่วมทีมยืนยันว่า "งานส่วนนี้คนนี้ทำจริง" |
| 1 (MVP) | หน้าพอร์ตส่วนตัว | รวมทุกโปรเจกต์ของคนนั้นไว้หน้าเดียว |
| 1 (MVP) | แบบประเมินและรอบการประเมิน | ตั้งหัวข้อ เกณฑ์ น้ำหนักคะแนน เปิด/ปิดรอบ กำหนดเดดไลน์ |
| 1 (MVP) | ให้คะแนน คอมเมนต์ และประเมินตัวเอง | บันทึกร่างได้ พอร์ตแสดงข้างฟอร์มตอนประเมิน |
| 2 | ประเมินรอบทิศ (360°) | เพื่อนร่วมงานและลูกน้องประเมิน ผลไม่ระบุตัวตน |
| 2 | เป้าหมาย KPI/OKR | ตั้งต้นรอบ ใช้เป็นเกณฑ์ปลายรอบ |
| 2 | เตือนเป็นรอบ | ถามทุกสองสัปดาห์ว่า "ช่วงนี้ทำอะไรเด่นๆ บ้าง" |
| 2 | แดชบอร์ดและส่งออก | ภาพรวมรายแผนก ส่งออก Excel/PDF |
| 2 | Audit log | บันทึกว่าใครแก้อะไรเมื่อไหร่ กันการแก้คะแนนย้อนหลัง |
| 3 | ดึงผลงานอัตโนมัติ | เชื่อม GitHub/GitLab/Jira เสนอรายการให้ผู้ใช้กดยืนยัน |
| 3 | ขั้นตอนอนุมัติผลและโต้แย้งผล | หัวหน้า → ผู้จัดการ → HR และพนักงานรับทราบหรือโต้แย้งได้ |
| 3 | แผนพัฒนารายบุคคล (IDP) | ต่อยอดหลังประเมิน |

## โครงสร้างข้อมูล

ตารางหลัก 10 ตาราง จุดสำคัญคือ Contribution เป็นตัวกลางที่เชื่อมพอร์ตเข้ากับการประเมิน

| ตาราง | ฟิลด์สำคัญ | เชื่อมกับ |
|---|---|---|
| Employee | ชื่อ, อีเมล, บทบาทที่ได้รับ (HR/แอดมิน), แผนก, ตำแหน่ง, หัวหน้า (manager_id) ซึ่งบทบาทหัวหน้าคำนวณจากฟิลด์นี้ | Team, Membership |
| Team | ชื่อทีม, แผนก | Employee, Project |
| Project | ชื่อ, คำอธิบาย, วันเริ่ม/จบ | Team, Membership |
| Membership | พนักงาน, โปรเจกต์, บทบาท, หน้าที่ | Employee, Project |
| Contribution | ผู้บันทึก, โปรเจกต์, รายละเอียด, impact, ลิงก์หลักฐาน, ทักษะ, สถานะยืนยัน | Membership, Endorsement |
| Endorsement | ผลงาน, ผู้ยืนยัน, ข้อความ (ไม่บังคับ) | Contribution, Employee |
| ReviewCycle | ชื่อรอบ, วันเปิด/ปิด, สถานะ | ReviewTemplate, Review |
| ReviewTemplate | หัวข้อ, เกณฑ์, น้ำหนักคะแนน | ReviewCycle |
| Review | ผู้ถูกประเมิน, ผู้ประเมิน, ประเภท (ตัวเอง/หัวหน้า/360°), คะแนน, คอมเมนต์, สถานะ | ReviewCycle, Employee |
| AuditLog | ใคร, ทำอะไร, เมื่อไหร่, ค่าก่อน/หลัง | ทุกตาราง |

**กติกาสำคัญ:**

- ผลงานที่หัวหน้าเติมให้ จะขึ้นพอร์ตหลังเจ้าตัวกดยืนยันเท่านั้น
- ผลงานที่เกี่ยวกับรอบที่ปิดแล้วต้องล็อก แก้ไขไม่ได้ ยกเว้นผ่านการบันทึกใน AuditLog
- ตาราง Review ประเภท 360° เก็บตัวผู้ประเมินไว้ในระบบ แต่ไม่แสดงให้ใครเห็น

## ขั้นตอนการใช้งานหลัก

ตลอดปีทุกคนสะสมผลงานไว้ในพอร์ต พอถึงปลายรอบ การประเมินก็ดึงจากพอร์ตนั้นมาใช้ต่อได้เลย

1. **ตลอดรอบ:** พนักงานบันทึกผลงานสั้นๆ พร้อมลิงก์หลักฐาน และระบุ impact
2. **ยืนยันผลงาน:** เพื่อนร่วมทีมกด Endorse งานที่เห็นว่าทำจริง ส่วนผลงานที่หัวหน้าเติมให้ เจ้าตัวต้องกดยืนยัน
3. **เปิดรอบ:** HR เลือกแบบประเมิน กำหนดเดดไลน์ และเปิดรอบ ระบบแจ้งเตือนทุกคน
4. **ประเมินตัวเอง:** พนักงานเลือกผลงานจากพอร์ตมาประกอบ แล้วให้คะแนนและเขียนความเห็นสั้นๆ
5. **หัวหน้าประเมิน:** หน้าจอแสดงพอร์ตของลูกทีมข้างฟอร์ม พร้อมคะแนนประเมินตัวเองเพื่อเทียบช่องว่าง
6. **ปรับเทียบ:** HR ดูการกระจายคะแนนรายแผนก ตรวจว่าหัวหน้าแต่ละคนให้คะแนนเข้มต่างกันหรือไม่
7. **ปิดรอบและล็อกผล:** ผลถูกล็อก ส่งให้พนักงานรับทราบ

## หลักการออกแบบเพื่อความเป็นธรรม

พอร์ตที่ดีไม่ได้ช่วยคนพูดไม่เก่งโดยอัตโนมัติ ถ้าออกแบบไม่ระวัง ระบบจะกลายเป็นเวทีใหม่ของคนที่เขียนเก่งแทน จึงต้องมีหลักเหล่านี้:

| หลักการ | ทำอย่างไร |
|---|---|
| ลดแรงเสียดทานในการกรอก | ใช้เทมเพลตสั้นๆ ไม่บังคับเขียนยาว แนบลิงก์แทนการอธิบายเอง |
| เสนอรายการให้ก่อน | เฟส 3 ดึงข้อมูลจาก GitHub/Jira มาเสนอ ผู้ใช้แค่กดยืนยันหรือเติมคำอธิบาย |
| เตือนเป็นรอบ | ทุกสองสัปดาห์ถามสั้นๆ จะได้ไม่ต้องนึกย้อนตอนปลายปี |
| ให้คนอื่นช่วยยืนยัน | Endorse จากเพื่อนร่วมทีม และหัวหน้าเติมผลงานให้ได้ (เจ้าตัวยืนยันก่อนขึ้นพอร์ต) |
| มีหมวดงานที่มองไม่เห็น | รีวิวโค้ด สอนน้องใหม่ ดูแลเอกสาร ต้องบันทึกได้โดยเฉพาะ ไม่งั้นระบบจะให้ค่าแต่งานที่โชว์ได้ |
| ห้ามนับปริมาณเป็นคะแนน | จำนวน commit หรือจำนวนรายการเป็นแค่หลักฐานประกอบ ไม่ใช่ตัวตัดสิน เพราะคนจะเกมระบบ และงานยากที่ใช้โค้ดน้อยจะเสียเปรียบ |
| ปรับเทียบหัวหน้า | HR ดูว่าหัวหน้าแต่ละคนให้คะแนนเข้มต่างกันแค่ไหน |

## เทคโนโลยีที่แนะนำ

เลือกชุดที่ทำเป็นเว็บแอปเดียวจบ ใช้ภาษาเดียวทั้งหน้าบ้านและหลังบ้านเพื่อให้ทำคนเดียวได้เร็ว

| ส่วน | แนะนำ | เหตุผล |
|---|---|---|
| เว็บแอป | Next.js + TypeScript | ได้ทั้งหน้าจอและ API ในโปรเจกต์เดียว |
| ฐานข้อมูล | PostgreSQL | ข้อมูลมีความสัมพันธ์เยอะ (ทีม โปรเจกต์ ผลงาน การประเมิน) เหมาะกับฐานข้อมูลแบบตาราง |
| ตัวช่วยเข้าถึงข้อมูล | Prisma หรือ Drizzle | นิยามตารางเป็นโค้ด และมี migration |
| ยืนยันตัวตน | Auth.js (NextAuth) | รองรับล็อกอินด้วยอีเมลหรือ Google/Microsoft ขององค์กร |
| สิทธิ์ | ตรวจที่ฝั่งเซิร์ฟเวอร์ทุกคำขอ | ห้ามพึ่งการซ่อนปุ่มที่หน้าจออย่างเดียว |
| เชื่อมระบบ (เฟส 3) | GitHub/GitLab/Jira API | ดึงรายการผลงานมาเสนอให้ผู้ใช้ยืนยัน |
| รายงานส่งออก (เฟส 2) | สร้าง Excel/PDF ฝั่งเซิร์ฟเวอร์ | ใช้กับ HR และผู้บริหาร |

## แผนพัฒนาและความเสี่ยง

เริ่มจากส่วนที่ทำให้พอร์ตใช้งานได้จริงก่อน แล้วค่อยต่อระบบประเมิน เพราะพอร์ตคือจุดเด่นและต้องสะสมข้อมูลล่วงหน้า

1. **ขั้นที่ 1:** ล็อกอิน สิทธิ์ และโครงสร้างองค์กร
2. **ขั้นที่ 2:** โปรเจกต์ ทีม บันทึกผลงาน Endorse และหน้าพอร์ต
3. **ขั้นที่ 3:** แบบประเมิน รอบประเมิน ประเมินตัวเอง และประเมินโดยหัวหน้า (จบ MVP)
4. **เฟส 2:** 360° เป้าหมาย เตือนเป็นรอบ แดชบอร์ด Audit log
5. **เฟส 3:** ดึงผลงานอัตโนมัติ ขั้นตอนอนุมัติ แผนพัฒนารายบุคคล

**ความเสี่ยงที่ต้องระวัง:**

- **ไม่มีคนกรอกผลงาน** ถ้ากรอกยาก ระบบจะว่างเปล่า แก้ด้วยฟอร์มสั้นและการเตือนเป็นรอบ
- **พอร์ตเอนเอียงไปทางคนเขียนเก่ง** แก้ด้วย Endorse การเติมแทน และการเสนอรายการอัตโนมัติ
- **คนเกมระบบด้วยปริมาณ** แก้ด้วยการไม่ใช้จำนวนรายการเป็นคะแนน
- **ข้อมูลรั่วหรือเห็นเกินสิทธิ์** แก้ด้วยการตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์และ Audit log
- **ไม่ระบุตัวตนไม่จริง** ในทีมเล็ก ผล 360° อาจเดาผู้ประเมินได้ ควรแสดงเฉพาะเมื่อมีผู้ประเมินตั้งแต่ 3 คนขึ้นไป
